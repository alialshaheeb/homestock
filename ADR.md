# Architecture Decision Records

## 1. Backend language/framework: Python + FastAPI
Date: 2026-09-30
Status: Decided
Context: HomeStock is a small JSON API run as one process, and I need request validation, easy unit testing and a language I can explain without notes.
Decision: I chose Python with FastAPI (served by uvicorn). It gives typed request validation and automatic API docs with very little code.
Alternatives considered: Flask, which I rejected because validation would need extra libraries; Django, which I rejected because its ORM, admin and auth are unnecessary for one SQLite file and two small domains.
Consequences: Few dependencies and simple tests through TestClient; I write the SQL myself with sqlite3, which keeps the data layer visible but means no migrations tool.

## 2. Two domains, Inventory and Restock, joined only through Inventory's service functions
Date: 2026-11-10
Status: Decided
Context: HomeStock does two separate jobs: tracking what is in the house (Inventory) and deciding what to buy (Restock list). Assignment 2 will run them as separate services with separate data, so the boundary has to be clean now even though both live in one process.
Decision: Each domain is its own package (inventory/, restock/) owning its own tables and routes. Restock never reads or writes Inventory's tables; it only calls the public functions in inventory/service.py (list low-stock items, restock an item), which become HTTP calls after the split. A shopping-list row stores the Inventory item id as a plain number, not a foreign key.
Alternatives considered: A shopping list that JOINs directly on the items table: simpler queries today, but it breaks as soon as each service owns its own database. Splitting by entity (locations vs items): rejected because an item cannot exist without its location, so the two halves would call each other on almost every request.
Consequences: Inventory can move into its own service without code changes on its side. The cost: Restock must copy what it shows (item name, unit) when it adds a row, and the database no longer stops a shopping-list row from pointing at a deleted item, so that case is handled in code.

## 3. Shopping-list rows reference Inventory items by a plain id and keep their own copy of name and unit
Date: 2026-11-10
Status: Decided
Context: The two domains share one SQLite file for now, but ADR-2 requires that each owns its tables. The shopping list still needs to point at the Inventory item it restocks.
Decision: Inventory keeps a real foreign key inside its own domain (items.location_id → locations.id, with CHECK constraints on quantities). shopping_list.inventory_item_id is a nullable plain INTEGER with no FOREIGN KEY, and name/unit are copied into the row when it is added. A partial UNIQUE index allows only one open entry per Inventory item.
Alternatives considered: A FOREIGN KEY from shopping_list to items: the database would guarantee the link, but it ties the two domains to one database and makes deleting an item fail while it is on the list. Storing only the id and looking up the name each time: no duplicated data, but every list view would need Inventory.
Consequences: The list renders on its own, and the split in Assignment 2 needs no schema change. Copied names can go stale if an item is renamed, and a row can point at a deleted item; mark_bought() handles that case and reports restocked=false.

## 4. Test the domain logic against a real SQLite file, and the routes only for HTTP behaviour
Date: 2026-11-10
Status: Superseded by [9]
Context: The 70% coverage bar is on core business logic. Most of HomeStock's rules (stock never below zero, what counts as low stock, one open list entry per item, buying restocks Inventory) are enforced partly in Python and partly by SQLite constraints.
Decision: Service tests call inventory/service.py and restock/service.py directly on a fresh temporary SQLite file per test, with no mocks, so the constraints are exercised too. Restock is tested against the real Inventory functions. Route tests only check status codes (201/204/404/409/422) and one end-to-end flow (low stock → list → bought → restocked). Coverage is measured on the inventory and restock packages.
Alternatives considered: Mocking the database or the inventory client: faster and more isolated, but it would not catch a broken SQL query or constraint, which is where most bugs here would be. Testing only through HTTP: covers everything at once, but failures point to the route instead of the rule.
Consequences: 42 tests run in about a second with 99% coverage of the two domains. Left thinner on purpose: the JavaScript UI (checked by hand in a browser) and the `python app.py` start-up line. When Restock calls Inventory over HTTP (Assignment 2), its tests will need a stub or a running Inventory service.

## 5. No user accounts or login
Date: 2026-11-10
Status: Decided
Context: HomeStock is used by one household on its own network: everyone who can open it is allowed to change the stock. Adding login was one of the free choices (§1b).
Decision: No authentication, user accounts or per-user data. Every request acts on the single household's data.
Alternatives considered: Session login with hashed passwords: needed if several households shared one deployment or the app were exposed to the internet, but it adds a users table, password storage, sessions and their tests, none of which serves the two domains being built. HTTP basic auth with one shared password: cheap, but gives a false sense of security over plain HTTP and is easy to leak.
Consequences: The code stays focused on Inventory and Restock, and there is no password data to protect. The app must not be exposed publicly as-is; before deploying it to the internet (Assignment 2), access control has to be added or the deployment restricted, and every table would need a household id if more than one household used it.

## 6. The split: Inventory and Restock as two services, each with its own database, joined only over HTTP
Date: 2026-11-20
Status: Decided
Context: Assignment 2 runs each domain as its own container with its own data. ADR-2 drew the seam in Assignment 1: Restock may only use Inventory's public functions, never its tables. The question was whether that seam still holds once those function calls become network calls.
Decision: Inventory (locations, items, stock changes) and Restock (the shopping list) are separate FastAPI services, each with its own Dockerfile, its own migrations folder and its own SQL Server database, reached with a login that has access to that database only. The only things crossing the seam are three HTTP calls from Restock to Inventory, all in services/restock/app/inventory_client.py: GET /items?low_stock=true (fill the list with what is running low), GET /items/{id} (copy the name and unit when an entry is added for an item) and POST /items/{id}/restock (add the bought amount back to stock). Inventory never calls Restock. The seam did not move: ADR-2's public functions became exactly these three endpoints.
Alternatives considered: One shared database with a schema per service: joins stay possible, but either service could still read the other's tables, and a migration in one could break the other. Moving "mark bought" into Inventory: it would avoid a write across the seam, but it puts shopping-list rules inside the stock service.
Consequences: Each service is built, deployed, migrated and scaled to zero on its own. Restock now depends on Inventory being reachable: when Inventory times out (INVENTORY_TIMEOUT_S, 2 s by default) or answers with a 5xx, Restock answers 503 with a clear message, the shopping list itself still loads, and "mark bought" changes nothing, because Inventory is called before the entry is marked. On Azure a cold Inventory can make the first Restock call fail; trying again works once it has started.

## 7. Data and migrations: one database per service, versioned SQL migrations, forward-only
Date: 2026-11-21
Status: Decided
Context: In Assignment 1 both domains lived in one SQLite file, created on first boot. Now each service owns its own database (SQL Server locally, Azure SQL serverless on Azure), and once a database holds data its schema has to change in place.
Decision: Each service has numbered .sql files in migrations/ that its own runner (app/migrations.py) applies at start-up, in order. Applied versions are recorded in a schema_migrations table, so a second start applies nothing, and each migration commits together with its record in one transaction. Applied files are never edited; a correction is a new, higher-numbered file. Inventory's three default places are seeded idempotently. No data was moved between databases: Assignment 1 was never deployed, so each service starts from its own 001_init.sql.
What was lost at the seam, and how it is compensated: the database can no longer guarantee that a shopping-list entry points at an existing item (no foreign key across databases). Restock checks the item with GET /items/{id} when an entry is added, copies the name and unit (ADR-3), and "mark bought" reports restocked=false if the item was deleted meanwhile. "Mark bought" also spans two databases with no shared transaction: Inventory is restocked first, then the entry is marked bought. If Inventory is down nothing changes (503); if the second step failed after the first, stock would be added while the entry stays open, a rare and visible case the user can fix by hand.
Recovery plan for a bad migration: because a migration and its record commit together, a migration that fails is rolled back completely, the new container does not start, and the CD health check fails, so the run is red and the problem is visible. The fix is a new migration (or a corrected one, if the failed one was never recorded), pushed through the same pipeline. If a migration succeeded but damaged data, Azure SQL's automatic backups allow a point-in-time restore to a new database, which the service is then pointed at through DATABASE_URL.
Alternatives considered: A migration tool such as Alembic or Flyway: more features (down-migrations, checksums), but another dependency and more to explain, for a handful of plain SQL files. Down-migrations: not required, and a down-migration that drops a new column also drops the data written to it.
Consequences: Schema history is in the repository and identical on every machine and on Azure. Migrations run at start-up, which is safe here because each service runs at most one replica, so two containers never migrate at the same time; with several replicas this would need a lock or a separate migration step in the pipeline. Every migration has to be written so that it keeps existing rows.

## 8. Serverless hosting on Azure: Container Apps, Azure SQL serverless on the free offer, and a Storage static website
Date: 2026-11-22
Status: Decided
Context: HomeStock has to run on my own Azure for Students subscription, be deployed only by the pipeline, and cost nothing while nobody uses it.
Decision: Everything is in one resource group, rg-aalshaheeb-ieu2024, in France Central (one of the five regions my subscription allows; Spain Central has no free SQL offer). Two Container Apps (aalshaheeb-ieu2024-inventory and -restock, Consumption plan, 0.25 vCPU and 0.5 GiB, minimum 0 and maximum 1 replica) in one environment, aalshaheeb-ieu2024-env, with the Log Analytics workspace Azure created for it. One logical SQL server, aalshaheeb-ieu2024-sql, with one serverless database per service (General Purpose, Gen5, 0.5 to 1 vCore) on the free offer, which pauses the database instead of billing when the monthly free allowance runs out. One storage account, aalshaheebieu2024ui, serving ui/ as a static website. Images live on GHCR as public packages. The pipeline signs in as a user-assigned managed identity, aalshaheeb-ieu2024-github, through OIDC, with Contributor on the resource group only.
Cost model: Container Apps bill per vCPU-second and GiB-second only while a replica runs, and the monthly free grant covers this app; the databases bill per vCore-second while online and only storage while paused, both inside the free offer; the storage account bills a few cents per GB and per request; Log Analytics is free up to 5 GB a month; public GHCR packages are free. Nothing has a fixed monthly cost, so there is no exception to justify.
Alternatives considered: App Service or a VM: always on, so they cost money while idle (out of scope). Azure Container Registry instead of GHCR: a fixed monthly fee for something GHCR does for free. Keeping minimum replicas at 1: no cold starts, but the app would be billed all day for a household that uses it a few times.
Consequences of scaling to zero: after a few idle minutes a service has no replica, so the first request starts one, and until uvicorn listens Azure answers 503 "App port is not ready" (I measured about 13 s for inventory, and up to 30 s). The UI retries reads with a "starting up" message and asks the user to retry writes. After 60 idle minutes a database pauses too, and the first connection resumes it, which takes up to a minute (error 40613 or timeouts meanwhile). Because the container has always scaled to zero before its database pauses, a paused database is always met at start-up, where connect_with_retry tries 30 times, 2 s apart; the CD health check waits up to 5 minutes for the same reason. A cold Inventory can make Restock's first cross-seam call time out (2 s): that action returns 503 and works when retried. Migrations run at start-up, which is safe only because there is at most one replica.
At 100x traffic: set a minimum of 1 replica (no cold starts for users) and a higher maximum with an HTTP scale rule; move migrations out of start-up into a pipeline step, since several replicas starting together would race; use a connection pool instead of one connection per request; move the databases off the free offer to a larger serverless or provisioned size; give Restock's calls to Inventory retries with backoff and cache the low-stock list briefly; and put a CDN in front of the static site.

## 9. Pipeline and testing: CI gates every commit, CD deploys main only after the same checks
Date: 2026-11-21
Status: Decided
Context: The services are deployed automatically from main, so the pipeline is the only thing standing between a broken commit and the live URL. Restock now talks to Inventory over HTTP, which unit tests with a fake Inventory cannot fully prove.
Decision: CI runs on every push and pull request; on main the CD workflow runs the same CI first. It gates on: ruff lint; each service's unit and API tests against a real SQL Server container, with at least 70% coverage per service; openapi.yaml matching the routes (a test regenerates the document and compares); system.yaml valid against system.schema.json and both OpenAPI documents valid; the integration test across the seam; and a successful image build. Images are pushed to GHCR, tagged with the commit SHA, only from main and only if every check passed, and CD deploys exactly those images, then waits until /health on both services answers 200 with that SHA. The cross-seam test (tests/integration) starts the real stack with docker compose (SQL Server, db-init, both services) with throwaway passwords, then checks: a low-stock item goes onto the list and buying it restocks Inventory; adding an entry for an item copies its name and unit, and an unknown item is a 404; with the inventory container stopped, Restock answers 503 with a clear message while its list and its /health still work.
Alternatives considered: Only the stub tests already in restock's unit tests (FakeInventory and respx): fast, but a stub can drift from the real Inventory API without any test failing. Running the integration test against Azure after deploying: closest to production, but a failing test would already be live.
Deliberately not tested: the JavaScript UI (checked by hand in the browser, including the cold-start message), Azure-only behaviour such as cold starts, the database resuming from pause and the OIDC sign-in (covered by the post-deploy health check and checked by hand), and performance under load.
Consequences: A commit reaches Azure only if the services, their contract and the documents agree. The integration job adds about two to three minutes to CI. This replaces ADR-4, whose SQLite-based tests no longer exist.
